# MT2S

A simulator for multi-model systems that keep their models consistent automatically, built to
answer one question: when a system generates its own updates to repair cross-model consistency,
what does that cost under concurrency?

This is the code behind *An Evaluation of Consistency-Aware Multi-Model Systems*.

## The idea

Organisations describe the same things in several models at once — a car's brake system and its
tyres both record a wheel diameter. Keeping those in step by hand serialises everyone's work, so
systems increasingly do it themselves: a write to one model triggers a consistency-preservation
rule (CPR) that updates the others. That removes the human bottleneck, and with it the
serialisation the humans provided. The repair updates now compete for the same data as everything
else.

Those rules form a graph over properties, and the simulator generates that graph from four
parameters: how many properties have an outgoing rule, how many rules a write triggers on average
and at most, and how concentrated the rule targets are. Transactions run under conservative
two-phase locking with cautious waiting, so nothing deadlocks and the only thing varying is the
shape of the rule graph.

The short version of what we found: the fraction of properties carrying a rule dominates
everything else. When it is high, cascades collide, transactions spend most of their life waiting
out abort backoff, and adding cores does not help. The maximum rules per write makes no
difference at all.

## Trying it

Java 17 and Maven:

    mvn -DskipTests package

One simulation of the base configuration, about a minute:

    java -cp target/ts-simulator-1.0.0-SNAPSHOT.jar \
         -Dts.wl.thetaRange=true -Dts.wl.thetas=0.5 \
         de.tum.tssimulator.experiments.WorkloadAlphaScan

The `theta = 0.50` row prints `tps 1883.0`, `cap_share 0.785`, `sdr 1.203`. Those are exact: the
engine is deterministic given a seed, so if your numbers differ, something in the build differs.

`mvn test` runs the test suite.

## Reproducing the paper

The measurement data is not in the repository — it is regenerated by running the experiments. The
full set is 230 cells at 5 seeds for the four axis sweeps, plus the parameter grids, the time
breakdown and the PostgreSQL comparison. `AGENTS.md` has the commands, the options each driver
takes, and the things that are easy to get wrong (one simulation per JVM, and why a single shard is
not a figure).

Afterwards, four Python scripts in `scripts/plotting/` turn the data into the paper's figures.

## What is where

    src/main/java/de/tum/tssimulator/
      cpr/           generates the CPR graph and computes closures
      bookkeeping/   the consistency-preservation updates a write triggers
      core/          transactions, groups, phases, time accounting
      execution/     admission control, processor units, dispatch
      locking/       two-phase locking variants and cautious waiting
      monitoring/    metrics
      experiments/   the experiment drivers
    scripts/
      campaign/      build, run and merge a campaign
      plotting/      the figure scripts
      postgres_anchor/   the PostgreSQL harness the simulator is validated against

The simulator is deliberately engine-agnostic: it measures what the rule graph costs, not what any
particular database does with it. It is validated against PostgreSQL to show the model behaves
like a real system over the range we use it in.
